# DEVELOPMENT_RULES.md

# Antigravity Development Rules & Engineering Constitution

**Project:** Siddharth Varpe — Premium Personal Portfolio  
**Deployment:** Vercel  
**Status:** MANDATORY  
**Purpose:** Prevent random, inconsistent, insecure, unnecessary, or unapproved implementation decisions.

---

# 1. READ THE DOCUMENTATION BEFORE WRITING CODE

Antigravity MUST NOT begin implementation by immediately generating code.

Before creating or modifying any feature, it MUST understand the project's source-of-truth documents.

Required reading order:

1. `PRD.md` — Product requirements and approved functionality
2. `TechStack.md` — Approved technology architecture
3. `SECURITY.md` — Mandatory security requirements
4. `DEVELOPMENT_RULES.md` — These engineering and implementation rules

If these documents are present in the repository, they are mandatory project context.

---

# 2. SECURITY.MD IS A HARD CONSTRAINT

`SECURITY.md` is NOT optional documentation.

It is the project's **security constitution**.

Antigravity MUST analyze `SECURITY.md` before implementing:

- authentication
- authorization
- admin pages
- APIs
- server actions
- forms
- contact functionality
- database operations
- file uploads
- media handling
- webhooks
- external integrations
- environment variables
- sessions
- passwords
- redirects
- caching
- logging
- deployment configuration
- payment-related functionality
- any feature involving user-controlled input

Security requirements must be incorporated during design, not added afterward.

---

# 3. SECURITY DOCUMENT ANALYSIS PROTOCOL

Before implementing a feature, Antigravity MUST perform this mental/checklist analysis:

### Step 1 — Identify the feature

Clearly determine:

- what is being built
- who can use it
- whether it is public or private
- whether it reads or writes data
- whether it communicates with external services

### Step 2 — Identify trust boundaries

Determine:

- what data comes from the browser
- what data comes from an authenticated administrator
- what data comes from MongoDB
- what data comes from external services
- what data is generated by the server
- what data is trusted
- what data must remain untrusted

### Step 3 — Match against SECURITY.md

Check the relevant security categories, including where applicable:

- XSS
- CSRF
- insecure file uploads
- path traversal
- SSRF
- password-reset security
- session management
- JWT secrets
- CORS
- rate limiting
- exposed environments
- default credentials
- webhook verification
- payment verification
- IDOR/BOLA
- API/user-input validation
- exposed logs
- exposed source maps
- authentication
- authorization
- database security
- privacy
- caching
- dependency security

### Step 4 — Design the secure implementation

The implementation MUST satisfy the applicable controls in `SECURITY.md`.

### Step 5 — Test the security boundary

The feature is not complete until the relevant security behavior is tested.

---

# 4. SECURITY TAKES PRIORITY

When requirements conflict:

**Security > Correctness > Product requirements > UX convenience > Visual preference > Implementation convenience**

Never weaken security merely because:

- implementation is harder
- development takes longer
- a UI looks cleaner without it
- a library requires extra configuration
- a security check causes an error
- the frontend appears to prevent the attack

If there is a conflict with `SECURITY.md`, the security requirement wins unless the user explicitly approves a change.

---

# 5. NEVER GUESS SECURITY DECISIONS

If Antigravity encounters an undefined security decision:

**DO NOT GUESS.**

It must:

1. identify the security concern
2. explain what could go wrong
3. propose secure implementation options
4. select/recommend the safest reasonable option
5. ask for approval if the decision materially changes security, privacy, authentication, authorization, or data architecture

Never silently choose the easiest implementation.

# 22. DATABASE RULES

Database:

**MongoDB Atlas**

Rules:

- database access is server-side
- never connect the browser directly to MongoDB
- use validated inputs

- use appropriate indexes
- paginate large collections
- never expose unnecessary database fields
- never expose database credentials

MongoDB is the source of truth for dynamic content and contact messages.

# 23. CONTACT FORM IS A CRITICAL FLOW

The contact form must actually reach the user.

Approved architecture:

```text
Visitor
   ↓
Contact Form
   ↓
Validation
   ↓
Cloudflare Turnstile
   ↓
Server-side verification
   ↓
MongoDB Atlas
   ↓
Resend notification
   ↓
User email
```

Important reliability rule:

**Persist the contact message in MongoDB before attempting email notification.**

If email delivery fails:

- preserve the message
- record delivery status
- show it in Admin Messages
- do not lose the submission

---

# 24. CONTACT MESSAGE PERMANENCE

- memory
- browser storage
- Vercel filesystem
- temporary server state


# 58. NEVER FIX ONE PROBLEM BY CREATING ANOTHER

Examples:

Do not fix:

- an auth error by disabling authentication
- a CORS error by allowing all origins
- an upload error by accepting every file type
- a database error by exposing the database to the browser
- a Turnstile error by skipping verification
- an email error by exposing the Resend API key
- an admin access issue by removing authorization
- a performance issue by removing important security controls

Find the correct underlying solution.

# 72. DECISION LOGIC

When deciding whether to implement something:

### If explicitly required:
Implement it.

### If explicitly prohibited:
Do not implement it.

### If necessary to make an approved feature function:
Implement the minimum required supporting behavior.

### If useful but not required:
Do not automatically implement it.

### If ambiguous:
Ask.

### If security-sensitive and ambiguous:
Stop and ask rather than guessing.

During development, Antigravity may discover ideas such as:

- new animations
- extra pages
- new analytics
- AI assistants
- blog
- newsletter
- comments
- authentication providers
- payment systems
- booking
- additional dashboards

These may be good ideas.

They are still **out of scope unless approved**.

Record them as suggestions instead of implementing them automatically.

---

# 74. PERFORMANCE + SECURITY BALANCE

Do not optimize by weakening security.

Do not secure the application by making it unusably slow.

Use proper engineering solutions such as:

- caching public data
- pagination
- indexes
- bounded queries
- lazy loading
- dynamic imports
- optimized assets
- server-side validation

Security controls must remain intact.

# 75. FINAL PRE-COMMIT REVIEW

Before committing a significant change, Antigravity should verify:

```text
[ ] Does this match PRD.md?
[ ] Does this use TechStack.md?
[ ] Did I analyze SECURITY.md?
[ ] Did I follow DEVELOPMENT_RULES.md?
[ ] Did I add anything that was not requested?
[ ] Did I invent any content or metrics?
[ ] Did I expose any secret?
[ ] Did I trust client-side authorization?
[ ] Did I validate external input?
[ ] Did I consider XSS/CSRF/IDOR/etc. where relevant?
[ ] Did I test mobile?
[ ] Did I test accessibility?
[ ] Did I test error states?
[ ] Did I preserve existing functionality?
[ ] Did I introduce unnecessary dependencies?
[ ] Did I create unnecessary architecture?
```

If any answer indicates a problem, fix it before completion.
